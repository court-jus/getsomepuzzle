# User scenarios

## Problem

The corpus contains puzzles generated according to different **pre-fill
modes** (`classic`, `sh`, `pathBased`, `syBased` — the `ProfileCategory`
enum in `equilibrium.dart`). But there are also **emergent scenarios**
that arise from the combinatorics of constraints alone, independently of
pre-fill: a puzzle with only NC plays like Minesweeper, a puzzle with
only CC/RC plays like a Hanjie, etc.

Today the `open_page` offers no scenario selector. Players cannot express
"I want a puzzle that plays like Minesweeper" — they must manually filter
by NC slugs, which is unintuitive for a non-technical player.

## Definition

A **user scenario** is a thematic label that describes the type of
**dominant reasoning** or **game feel** of a puzzle. It sits one level
above individual constraints: multiple slug combos can lead to the same
scenario, and a scenario can group puzzles generated by different methods.
The scenario is orthogonal to **difficulty** (which belongs to the
collection level).

Guiding principle: **one vocabulary, one detector.** The user scenario
reuses the `ProfileCategory` enum values already used by generation
balancing — no parallel names or mapping table are introduced. The only
additions are extending this enum to emergent scenarios and extending the
single `detectPuzzleProfile` detector to recognise them. The labels
displayed to the player are provided by l10n.

## Identified scenarios

`ProfileCategory` carries the eight canonical values. Four come from the
**generation mode** (stamped as `scenario:<name>` in the v2 line and
authoritative), four are **emergent** (deduced from present slugs):

| Value (`ProfileCategory`) | Origin | Composition / detection | Game equivalent |
|---------------------------|--------|-------------------------|-----------------|
| `classic`     | generation (default) or fallback | no dominance | general puzzle |
| `sh`          | generation (`preFillSh`) **or** emergent (slug SH present) | at least one SH | shape placement |
| `pathBased`   | generation (`preFillPath`, constructive algo) | marker only | routing/letters |
| `syBased`     | generation (`preFillSy`) | marker only | symmetry |
| `minesweeper` | emergent | `{NC, EY}` ≥ threshold, NC present | minesweeper |
| `nonogram`    | emergent | `{CC, RC, CT, RT}` ≥ threshold | hanjie/nonogram |
| `local`       | emergent | `{DF, FM}` ≥ threshold | forbidden patterns |
| `group`       | emergent | `{GS, GC}` ≥ threshold | group topology |

`pathBased`/`syBased` are **not** detected emergently: a legacy
LT-dominant or SY-dominant unmarked puzzle stays `classic`. Only `sh` has
emergent detection (presence of slug SH), which extends the legacy
heuristic already in `detectPuzzleProfile`.

### Detection rules

Detection is carried by the **single `detectPuzzleProfile` function**
(`equilibrium.dart`), extended to return all eight values. For a v2 line,
the first matching rule applies:

1. **`scenario:<name>` marker**: if the name is `pathBased`, `syBased`
   or `sh` → return it (authoritative, short-circuit). If the name is
   `classic` or unknown (e.g. `martian`) → **do not short-circuit**,
   proceed to emergent. This allows a puzzle generated as `classic` but
   composed of 100 % NC to reveal itself as `minesweeper`.
2. **Emergent**, from the constraint slugs multiset (repeats counted):
   - slug `SH` present (≥1) → `sh`;
   - otherwise, a group matches when `count(group) / total ≥ kEmergentThreshold`:
     - `minesweeper`: group `{NC, EY}` **and** `count(NC) ≥ 1`
       (a 100 % EY puzzle without NC stays `classic`);
     - `nonogram`: group `{CC, RC, CT, RT}`;
     - `local`: group `{DF, FM}`;
     - `group`: group `{GS, GC}`;
   - otherwise → `classic`.

`kEmergentThreshold` is `0.80`; its tolerance to stray slugs (below the
complement, i.e. ≤20 %) allows classifying a puzzle into its dominant
scenario. The exact value will be calibrated with use. Since the four
groups are mutually exclusive above 0.80, their order does not matter.

### Emergent threshold calibration (measured on the shipped corpus)

Sweep of `kEmergentThreshold` on a 10 % sample of the playable corpus
(`assets/*`, generator rejection files excluded — 53,104 puzzles total,
n=5311):

| Scenario | t=0.70 | t=0.80 | t=0.90 | t=1.00 (exclusive) |
|----------|-------:|-------:|-------:|-------:|
| `classic`     | 60.5 % | 66.3 % | 72.1 % | 77.5 % |
| `sh`          | 15.0 % | 15.0 % | 15.0 % | 15.0 % |
| `pathBased`   | 1.6 %  | 1.6 %  | 1.6 %  | 1.6 %  |
| `syBased`     | 1.7 %  | 1.7 %  | 1.7 %  | 1.7 %  |
| `minesweeper` | 12.3 % | 10.5 % | 6.5 %  | 1.6 %  |
| `nonogram`    | 3.9 %  | 1.6 %  | 0.7 %  | 0.6 %  |
| `local`       | 2.6 %  | 1.9 %  | 1.7 %  | 1.7 %  |
| `group`       | 2.4 %  | 1.6 %  | 0.8 %  | 0.4 %  |

`sh`/`pathBased`/`syBased` are invariant to the threshold (`sh` = marker
+ "SH present", tested before groups; the other two are marker-only).
Only the four emergent buckets migrate: the higher the threshold, the
more they drain into `classic`. `minesweeper` is the most sensitive (most
Minesweeper-feel grids carry 1–2 stray constraints, hence the sharp drop
under strict exclusivity).

**Decision: keep `0.80` for now.** It is the compromise that keeps all
four buckets visible without diluting the gameplay promise. Small buckets
(~1 %) are not negligible: at corpus scale (>50 k) this represents several
hundred puzzles, and they will also be fed by explicit scenario generation
(see "Generation with scenario"). They are therefore not hidden from the
selector.

### Detector shared with balancing

`detectPuzzleProfile` returns all eight values, but the generation
balancing currently only reasons about the four pre-fill modes. The
equilibrium **therefore collapses the four emergent values into the
`classic` bucket** via a collapse helper (`generationBucket`) applied at
every consumption point. Since these puzzles already counted as `classic`
before, generation behaviour is unchanged. The `kTargetProfile`
distribution, the `ProfileTarget` class, and the `switch` in
`worker_io.dart` continue to operate on the four generation values.

### Storage: derived, not serialised

`generationScenario` (on `Puzzle`) remains the **only stored marker** and
is round-tripped in the v2 line (`scenario:<name>`). The user scenario is
**derived**: lazily initialised on first read via
`detectPuzzleProfile(lineRepresentation)`, never serialised. It is
exposed:
- on `Puzzle`, in a `userScenario` field placed **next to**
  `generationScenario` (clarity: two distinct notions, generation vs
  feel);
- on `PuzzleData`, in a `userScenario` field computed in the constructor
  via the same detector (logic not duplicated), used by the filter.

## User interface

### In `open_page`

A **single-select** scenario dropdown in the
"advanced filters" section (the `DropdownButton` of `_buildAdvancedFilters`):

```
[Scenario dropdown]
   ▸ Any scenario (default — no filter)
   ▸ Classic
   ▸ Shape          (sh)
   ▸ Path           (pathBased)
   ▸ Symmetry       (syBased)
   ▸ Minesweeper
   ▸ Nonogram
   ▸ Local
   ▸ Group
```

Each entry shows a title (l10n label) and a description subtitle
(`scenarioExplain<Name>`). The internal value is the `ProfileCategory`
enum name. The order is fixed by the implementation.

Behaviour:
- **Independent** filter that adds to the rules (wantedRules / bannedRules)
  without modifying them.
- `applyFilter(newScenario:)` updates `Filters.wantedScenario`, persists
  via `.save()`, and recalculates `matchingCount`.
- During **onboarding**: recommended scenario = `null` ("Any"). A
  non-null scenario lights up the **shared override banner** via
  `_filtersMatchRecommendation()` (compares `wantedScenario == null`), and
  its reset (`_resetToRecommendation()`) sets the scenario back to `null`.

### l10n

Each scenario has a **translation** (title + description) in every
locale, plus a selector label and the "Any" entry. Keys
`scenario<Name>` (title) and `scenarioExplain<Name>` (description,
displayed as subtitle of the `DropdownMenuItem`). As with constraints,
the list is finite and fixed: dedicated ARB entries, no dynamic label
generation.

### Addition to `Filters` (`database.dart`)

`Filters.wantedScenario : ProfileCategory?` (`null` = "all"), persisted
in `SharedPreferences` like other filters (key
`wantedScenarioFilter`, serialised by `.name` via `Filters.load`/`save`).
The `_matchesFilters` predicate compares it against each puzzle's
`PuzzleData.userScenario`; the `_notPassed` sentinel (in `applyFilter`)
distinguishes "not passed" from explicit `null`.

## Generation with scenario

The generator could eventually produce puzzles for a given scenario
(e.g. `requiredRules = {'NC'}` for a minesweeper, or a `scenario`
parameter to the worker). This part is future — the immediate priority is
filtering in the existing corpus. When it arrives, the `generationBucket`
helper is the single point to evolve in order to give emergent scenarios
their own equilibrium targets.
